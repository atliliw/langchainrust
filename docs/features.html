2.2 with_structured_output

给个 schema，一步拿到强类型对象。传统做法是"提示模型输出 JSON → 手动解析 → 出错容错 → 再转成类型"，又烦又容易坏。框架把整套流程打包：传入 struct 派生 JsonSchema，即拿到类型安全、编译期可校验的解析结果。

Provider 自带方法（推荐）

OpenAIChat / OpenAICompatibleChat / OllamaChat 上的 chat.with_structured_output::<T>()，把 schema 作为 strict 工具声明绑定，同步返回方法对象，invoke 后直接从结构化工具参数解析出类型 T

StructuredOutputExt 泛用 trait

对所有 BaseChatModel 自动实现；入参手写 JSON Schema + 提示词，注入 system 消息，输出经 JsonOutputParser 剥 markdown 代码块、容错修复后反序列化

2.3a 提示词注册表（PromptRegistry）

PromptRegistry 给提示词一个只增不改、可寻址、可审计的登记处，机制是命名空间 + 版本号 + 内容哈希三位一体。解决 prompt 散落、线上变差查不出是哪次改的、回滚要重新发版等问题。

核心价值：负责任地管理提示词——每次注册算 SHA-256，版本号 + 哈希可寻址，回滚不覆盖而是作为新版本重新发布，审计链不断。

命名空间

斜杠分隔路径，如 customer/support/zh，非法返回 InvalidNamespace

版本号 + 哈希

每次注册带版本号与内容 SHA-256，variables 注册时解析好

三种定位

最新版 / 钉版本号 @n / 按内容哈希前缀，均可 resolve

线程安全

RwLock 并发安全，所有操作 &self，Arc 多组件共享

PromptRegistry 用法

rust 
use langchainrust::{PromptRegistry, VersionSpec};

let registry = PromptRegistry::new();
let v1 = registry.register("customer/support/zh", "你是客服。问题:{question}")?;
let v2 = registry.register("customer/support/zh", "你是资深客服,先共情再回答")?;
assert_eq!(v1.version, 1);

let latest = registry.get("customer/support/zh")?;            // 最新版
let pinned = registry.resolve("customer/support/zh", &1.into())?;  // 钉版本号
let tpl = registry.fetch("customer/support/zh@3")?;            // 文本引用

注意：注册表是纯内存的，进程退出即丢失；不自带持久化、远程分发或鉴权，跨进程共享需应用侧存库、启动时灌入。

2.5 LLM Cache

LLM 缓存缓存 LLM 响应，减少 API 调用、降低成本、改善重复查询的响应延迟。

核心价值：缓存相同请求，重复查询可降低高达 90% 的 API 成本。

内存缓存

进程内快速缓存，零依赖

TTL 过期

基于时间的缓存过期

容量上限

max_entries 限制条目数，防内存膨胀

手动旁路

build_key 判键、get/put 读写，接入自定义路径

内存 LLM 缓存

rust 
use langchainrust::core::cache::{CacheConfig, LLMCache};
use std::time::Duration;

// Configure the cache (TTL + entry cap)
let cache = LLMCache::with_config(
    CacheConfig::new().with_ttl(Duration::from_secs(3600))
);

// LLMCache 是独立组件,手动接入调用路径:build_key 判键,get/put 读写
let messages = vec![Message::human("What is Rust?")];
let key = LLMCache::build_key(&messages, "gpt-4o")?;

let result = if let Some(hit) = cache.get(&key).await {
    hit.result
} else {
    let fresh = llm.chat(messages, None).await?;
    cache.put(key, fresh.clone()).await;
    fresh
};
✓ 缓存最佳实践
  • 确定性查询：相同输入始终需要相同输出时缓存效果最佳
  • TTL 调优：根据数据新鲜度需求设置合适的 TTL
  • 容量上限：用 with_max_entries 限制条目，防止内存膨胀

use langchainrust::{RunnableExt, RunnableLambda, RunnableParallel};

let doubler = RunnableLambda::new_sync(|x: i32| x * 2);

4.3 Document Chains

文档处理链通过结合 LLM 调用与不同策略来处理多文档：Stuff、Refine、MapReduce 和 MapRerank。

核心价值：以不同的速度、成本和质量权衡处理大量文档。

策略方式适用场景Token 用量

5.1 Agents

Agent 是 LangChainRust 的核心组件，使 LLM 能够自主决策、调用工具并执行多步骤任务。

核心价值：将复杂问题分解为步骤，自动选择合适工具，迭代直至任务完成。

6.5 Hybrid Retrieval

6.6 MultiQueryRetriever

MultiQueryRetriever 用 LLM 把一个查询改写成多个变体，分别检索后合并去重，提高召回率。专门应对用户提问措辞与文档术语不一致、同义别名、短查询意图未展开等召回不足问题。

工作方式：用户查询 → LLM 生成 N 个变体 → 分别检索 → 合并去重 → 返回结果。

查询改写

LLM 把原查询改写为 N 个变体，覆盖同义词、缩写、口语

并行检索

每路调用底层检索器，返回 k_per_query 条

合并去重

同一文档被多路查到只保留一份

截断返回

final_k 控制喂给下游的最终结果数

MultiQueryRetriever 用法

rust 
use langchainrust::{MultiQueryRetriever, SimilarityRetriever, OpenAIChat};

6.7 HyDE 检索器

HyDE（Hypothetical Document Embeddings） 解决"查询太短、与文档不匹配"：先用 LLM 生成一个假设性答案（可能不准确），再用假设答案的嵌入去检索真实文档。假设答案措辞更接近真实文档，检索效果更好。

工作方式：用户查询 → LLM 生成假设文档 → 用假设文档检索 → 返回真实文档。

生成假设文档

LLM 把短查询补成与真实文档同风格的长文

假设文档检索

向量化由底层检索器处理，无需单独嵌入参数

返回真实文档

排序发生在假设↔真实之间，最终返回真实文档

双路并入

可选把原始查询与假设一起检索，降低带偏风险

HyDERetriever 用法

rust 
use langchainrust::{HyDERetriever, SimilarityRetriever, OpenAIChat, OpenAIEmbeddings};

let base_retriever = Arc::new(SimilarityRetriever::new(store, embeddings));

let hyde = HyDERetriever::new(llm, base_retriever)
    .with_k(5)
    .with_include_original_query(true);

let docs = hyde.retrieve("Rust concurrency").await?;

注意：假设答案本身可以是错的——它只是用来"对齐措辞"，真正返回的还是检索到的真实文档。底层检索器是 Arc<dyn RetrieverTrait>，BM25、向量、混合都能接。

6.9 Contextual Retrieval

Contextual Retrieval（Anthropic 提出）是索引期增强：ContextualEnhancer 在索引期用一个小 LLM 为每块生成 1-2 句上下文说明，拼在原文前面入库，检索命中率显著提升。

核心价值：把"孤立分块"变成"带上下文的分块"，解决块与块之间主题割裂导致的漏召回。

幂等

已带 contextual_context 的文档自动跳过，不重复叠加

fail-open

单块 LLM 失败只记 warning，用原文入库，不阻塞索引

并发可控

with_max_concurrency 控制并发，默认 4

小模型省钱

每块一次 LLM 调用，建议用便宜小模型控制成本

ContextualEnhancer 用法

rust 
use langchainrust::retrieval::contextual::{ContextualConfig, ContextualEnhancer};

let enhancer = ContextualEnhancer::new(llm) // 建议小模型控制成本
    .with_config(ContextualConfig::new().with_max_concurrency(4));

let docs = vec![Document::new("Revenue grew 3% year over year.")];
let enhanced = enhancer.enhance_documents(&docs).await;

注意：上下文说明写入 metadata["contextual_context"]，可检索、可审计；之后照常 index_documents(enhanced)。

6.10 语义缓存（SemanticCache）

CachedRetriever 包装任意 RetrieverTrait：词法命中（查询完全相同）直接返回缓存且跳过 embedding；否则对缓存条目算余弦相似度，超阈值即视为同义查询命中。大幅降低重复查询的检索成本。

核心价值：语义等价查询直接命中缓存，不必每次重新 embedding + 检索。

两级命中

词法命中零成本；语义命中按余弦相似度阈值判定

k 参与身份

同查询不同 k 各自缓存，互不串用

容量 / TTL

with_max_entries FIFO 容量 + 可选 with_ttl 过期

自动失效

add_documents 自动 invalidate，语料更新不脏

CachedRetriever 用法

rust 
use langchainrust::retrieval::{CachedRetriever, SemanticCacheConfig};

let cached = CachedRetriever::new(
    Arc::new(inner_retriever),   // 任意 RetrieverTrait
    Arc::new(embeddings),        // 用于给查询算向量
    SemanticCacheConfig::new()
        .with_threshold(0.95)    // 语义命中阈值
        .with_max_entries(256)   // FIFO 容量
        .with_ttl(Some(Duration::from_secs(600))),
);

let docs = cached.retrieve("apple", 3).await?; // miss → 检索并缓存
let fast = cached.retrieve("apple", 3).await?; // 词法命中，零成本

注意：语料更新后需手动 cache().invalidate() 或依赖 add_documents 自动失效。配合护栏时把 GuardedRetriever 放内侧。

6.11 重排序（Reranking）

重排序器 对检索结果重新评分，把最相关的排到前面，提高精确度。定位是"召回之后、喂给模型之前"的一道精排工序，配合 MultiQuery / HyDE 这类"扩大召回"的增强器搭配使用。

核心价值：先扩大召回、再精排，兼顾召回率与精确度。

KeywordReranker

关键词匹配打分，零嵌入、零模型调用、可离线

BM25Reranker

词频饱和 + 文档长度归一化 + IDF，with_params(k1,b) 可调

神经重排序

Cohere / Jina 交叉编码器，查询与候选联合打分，精度更高

统一执行器

RerankingExecutor 调度，with_top_n 固定返回量 + with_min_score 过滤

KeywordReranker 用法

原子写入

维度验证

建库固定维度，塞错维度向量直接报错

删除诚实

删不存在的文档返回 DocumentNotFound，不假装成功

A.12 Best Practices

01 Agent 选择

优先使用 FunctionCallingAgent（更可靠），本地模型用 ReActAgent。

02 模型选择

Agent 推荐 gpt-4，简单对话用 gpt-3.5-turbo，多模态用 Gemini。

03 记忆选择

长对话用 SummaryBufferMemory，短对话用 BufferMemory，超长用 ContextWindow。

04 RAG 策略

简单用 RetrievalQA，质量要求高用 CorrectiveRAG，关系密集用 GraphRAG，自适应用 AdaptiveRAG。

05 模型路由

可靠性用 Fallback 策略，成本用 LowestCost，速度用 LeastLatency。

06 缓存

重复查询启用 LLM 缓存，离线批量处理用 Batch API（成本降 50%）。

07 文档策略

少量小文档用 Stuff，大量文档用 MapReduce，精度要求高用 MapRerank，关系密集用 GraphRAG。

08 可观测性

生产环境用 Tracing (Tracer + SpanGuard) 监控，分布式追踪用 OTel 后端。

09 安全

用 Guardrails 做输入/输出验证，API Key 用环境变量，绝不硬编码。

10 CRAG 评分

用 with_grader_llm() 注入不同 LLM 做幻觉检测，避免自我验证偏差。
